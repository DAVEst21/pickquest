# CU-03 — Consultar progreso de aprendizaje

La ruta protegida `/progreso` consulta `GET /progreso` con el JWT de la sesión. El endpoint toma el estudiante exclusivamente del token; no acepta un identificador de estudiante del cliente. Usa una transacción de lectura RepeatableRead para obtener una instantánea coherente. Consultar, seleccionar detalles y reintentar no escriben datos ni conceden XP, QP, logros o bonificaciones.

## Datos disponibles

- XP acumulada y saldo QP: campos reales del estudiante.
- Nivel: `calcularNivel(xpTotal)`, compartido con la evaluación de retos. No confía en el nivel almacenado. La curva existente es 500 XP por nivel, expresamente provisional en `nivel.ts`; la pantalla lo indica. Este cambio no la convierte en una regla aprobada.
- Fases completadas: reutiliza `resumirIntentos` y `calcularEstadosFases` de CU-01. Se requieren todos los retos aprobados y al menos un reto por fase.
- Promedio de estrellas: media de la mejor marca histórica de cada reto con intentos, sin redondear previamente las medias por fase. Usa la misma base de mejores marcas de CU-01 y la etiqueta explica el denominador. Un reintento no duplica el reto en la media. Los intentos evaluados no aprobados también son resultados; solo la ausencia de intentos evaluados activa la bienvenida.
- Siete categorías SDLC, independientes del número y orden de fases. Nivel leído de `HabilidadSDLC` cuando existe un registro para esa categoría. Sin registro, no se supone nivel cero o uno.
- Fases contribuyentes: relación explícita `FaseHabilidad`, permite varias fases por categoría y varias categorías por fase. No se deduce del nombre, tema ni orden.
- Trofeos: únicamente `LogroEstudiante` del estudiante autenticado. El detalle muestra la condición de obtención registrada, fecha y rareza si está configurada. Sin reclamar recompensas ni listar logros no obtenidos.

## Definiciones pendientes y límites reales

No se encontraron configuraciones acordadas en el repositorio para:

1. Confirmación de la tabla de progresión de nivel.
2. Precisión: denominador, selección de intentos y ponderación.
3. Tiempo promedio: inicio/fin, pausas, reintentos y tratamiento de datos incompletos. Actualmente no se registra duración; `creadoEn` por sí solo no permite calcularla.
4. Dominio por habilidad y fase, umbrales de nivel de habilidad y relación curricular entre las fases existentes y las siete categorías.
5. Catálogo de logros, condiciones verificables, rarezas y proceso que registra su obtención. El esquema admite consultar logros ya registrados; no se crea ningún catálogo ni se otorgan trofeos al consultar.
6. Racha: actividad que cuenta, zona horaria por estudiante, corte diario, política de inactividad y tabla de multiplicadores. No hay registro de zona horaria del estudiante ni política configurada. Los contadores `RachaEstudio` existentes no se actualizan al enviar intentos, y su última actividad es una fecha sin hora. No se presentan como una racha vigente ni se deduce una política de los intentos. La consulta devuelve null hasta implementar las definiciones acordadas. El HUD heredado conserva su comportamiento previo; sus contadores no se usan como evidencia en CU-03.

Los datos pendientes se devuelven como `null` y se muestran como «No disponible» con una explicación, nunca como un cero o multiplicador inventado. Por tanto, **CU-03 no está completo respecto de los cálculos pendientes**. No se incorpora UTC-5, benchmarks, nombres, umbrales ni recompensas de Stitch. La configuración real de racha deberá integrarse también al registro de actividad y al otorgamiento de QP de CU-02, con pruebas de medianoche, DST, días duplicados e inactividad, una vez acordada.

## Migración y operación

Ejecutar `npm run prisma:generate` y `npm run prisma:deploy` en backend antes del arranque de la nueva versión. La migración `20261007010000_progreso_consulta` agrega las siete categorías conservando las tres heredadas, la relación curricular y rareza nullable. No transforma las categorías heredadas ni asigna datos por conjetura. No cambia el seed.

El frontend invalida la consulta al enviar un intento. La caché se limpia al cambiar/cerrar sesión. Header, footer y layout se reutilizan; Ficha Dev continúa separada. La navegación móvil permite acceder a la nueva sección y marca el enlace activo.

## Verificación

- `docker compose exec -T backend npm test -- --runInBand`
- `docker compose exec -T backend npm run test:e2e`
- `docker compose exec -T backend npm run build`
- `docker compose exec -T frontend npm run build`
- `docker compose exec -T frontend npm run lint`

`backend/test/progreso.e2e-spec.ts` usa fixtures identificados y eliminados al finalizar: autenticación, estado inicial, aislamiento entre estudiantes, mejores marcas sin duplicación, nivel derivado del XP, múltiples categorías para una fase, detalles de logros, datos pendientes, ausencia de escrituras y recuperación tras error. Los fixtures no pertenecen al seed ni se presentan como datos reales.

Comprobación de navegador: `frontend/test/progreso.browser.cjs` ejecutada con Chromium/Playwright, conexión y sesión reales más fixtures HTTP exclusivos de prueba para los detalles aún sin catálogo. Verificó enlace desde la pantalla principal, estado activo, navegación móvil, breadcrumb independiente de Ficha Dev, las siete categorías, fases contribuyentes, las tres rarezas, bienvenida, carga, error y reintento. Sin desbordamiento horizontal a 320, 390, 768, 1280, 1440 y 1920 px. Capturas de escritorio y móvil inspeccionadas. Requiere la app en localhost, el usuario demo del seed y Playwright instalado aparte (`NODE_PATH=/ruta/node_modules node frontend/test/progreso.browser.cjs`).

Resultado de validación: 51 pruebas unitarias y 32 e2e aprobadas, compilaciones de frontend/backend y lint de frontend/archivos backend modificados sin errores.
